# Vision

## Why Aruo exists

Repository quality is fragmented across generators, package managers, CI services, documentation systems, linters, release tools, and unwritten maintainer knowledge. Developers can create a runnable project quickly but still struggle to keep it secure, understandable, reproducible, and easy to evolve.

Aruo exists to make engineering intent durable. It should tell maintainers what a repository promises, what evidence supports those promises, how it differs from policy, and how to improve it without surrendering ownership of the codebase.

## Five-year destination

Aruo should become the local-first engineering operating system for a repository and, optionally, a fleet: project creation and adoption; health analysis; safe standards upgrades; documentation and onboarding; release and migration orchestration; reproducible benchmark evidence; and architecture assistance grounded in verified facts.

The CLI, schemas, policy formats, and evidence remain useful without an Aruo account. An optional hosted system may add collaboration and fleet history, never gate the core workflow.

## What Aruo must never become

- a template catalog that abandons repositories after generation;
- a universal build system that replaces Cargo, Go, uv, npm, or other native tools;
- an opaque score that confuses file presence with engineering quality;
- an autonomous agent that mutates, publishes, or releases without an inspectable plan;
- a plugin marketplace that treats popularity as security review;
- a cloud service that holds projects hostage;
- an accumulation of unsupported templates, flags, and integrations;
- a mechanism for enforcing one language’s conventions on every ecosystem.

## Success

Success is measured by safe upgrade rates, local/CI parity, time to a first verified result, newcomer task completion, useful finding acceptance, release reliability, and long-term retention—not repositories generated or checks counted.
